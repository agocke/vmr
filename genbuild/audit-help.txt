genbuild read audit (Linux, Python 3.9+, stdlib only)
==================================================

This opt-in observer DOES NOT sandbox a process or prove build hermeticity.
It reads an unmodified standalone genbuild Ninja graph and its invocation JSON.
It never changes the graph, sidecars, app, toolset, or product files itself.
The command being traced still executes normally and may write its outputs.

Run from the VMR root. Use your privately installed strace's absolute path:

  python3 -B genbuild/audit.py catalog \
    --root /absolute/external-dotnet \
    --directory /absolute/external-dotnet/host/fxr \
    --directory /absolute/external-dotnet/shared/Microsoft.NETCore.App \
    --output runtime-files.json

  python3 -B genbuild/audit.py catalog --directory /sys/devices/system/node \
    --output numa-membership.json

  python3 -B genbuild/audit.py trace --strace /absolute/path/to/strace \
    --graph /absolute/project/obj/genbuild/build.ninja \
    --cwd /absolute/project --output audit-capture \
    -- ninja -f /absolute/project/obj/genbuild/build.ninja -j 1

  python3 -B genbuild/audit.py analyze --capture audit-capture \
    --runtime-catalog runtime-files.json --platform-catalog platform-files.json \
    --platform-catalog numa-membership.json \
    --allow-runtime-proc --allow-case-sensitivity-probe \
    --report audit-report.json

The capture directory must not already exist. --cwd is Ninja's effective working
directory, not the directory containing build.ninja. Avoid Ninja -C unless it
matches --cwd; initial cwd is inherited and subsequent chdir calls are tracked.
Use absolute --graph paths to avoid ambiguity. -j 1 is only a suggested small
first smoke: multiple Ninja jobs are supported. Capture a command that actually
executes actions; an up-to-date/no-op graph is reported incomplete.

trace invokes exactly:
  STRACE -ff -ttt -yy -v -s 65535 -e trace=%file,%process,getdents64 \
    -o CAPTURE/trace -- COMMAND [ARG...]
It records capture.json (cwd, argv, graph path, SHA256 of graph and sidecars,
completion status, commandExitCode) and trace.PID files. trace returns the command
status; analyze independently rejects failed/interrupted captures. Preserve the
graph, sidecars and filesystem/symlink layout until analysis completes. Analyze
verifies graph/sidecar hashes against capture.json. Re-run analyze with edited
platform catalogs without executing any products. Keep catalogs/reports outside
the runtime catalog root; never catalog a workspace or home directory wholesale.
Catalog output inside its root and reports overwriting capture/graph/catalog
inputs are rejected.

Selected-stop capture (separate trace opt-in)
---------------------------------------------
Add trace --seccomp-bpf to retain EXACTLY the same syscall selection while asking
strace to stop only for selected syscalls. This is not a read allowance, parser
exception or sandbox. Default trace behavior is unchanged.

The option first runs a bounded (15-second) same-filter Python startup probe with
-d. It requires successful exec/exit, parseable complete logs, an enabled-filter
message AND live EVENT_SECCOMP stops attributed to that probe's actual PID.
Capability-test events alone, disabled/unavailable/oversized filters, warnings,
failed startup or a changed tracer do not establish activation. Probe diagnostics
over 4 MiB are rejected and retained, never silently truncated.

The actual workload runs WITHOUT -d. Its stderr is preserved in strace-stderr.log
and forwarded normally. Any strace-prefixed diagnostic other than ordinary
"Process PID attached", including any seccomp fallback warning, rejects verification
even if the command exits zero. Installation failures are fatal in strace's
source; this check also rejects startup fallback and other observed tracer
errors. Non-strace task diagnostics do not themselves invalidate capture.

capture.json records seccompBpf: requested/verified, selection, tracer SHA256,
probe argv/PIDs/live stops, actual argv, rejected diagnostics and limitations.
Probe logs and actual stderr are added to the hashed capture inputs. Analyze
rejects an unverified policy or changed evidence, disabling response-file
admissions as for any other incomplete capture. Preserve seccomp-preflight/
alongside the main logs. No production per-stop debug stream is generated.

This contract follows strace v7.3's filter_seccomp.c and strace.c; use a trusted
tracer. Unsupported tracer/kernel combinations fail the probe, not silently
downgrade. --seccomp-bpf requires launch plus follow-forks; do not combine attach,
detach-on-exec or syscall-limit modes. Unknown raw events still fail analysis.
Other higher-priority seccomp filters can suppress notifications, including
USER_NOTIF-mediated execution. This profile does NOT monitor installation of
competing filters, nor guarantee observation of adversarial tracees. The startup
probe is evidence of activation, not proof against later unreported kernel/tool
bugs. Original incomplete traces cannot be repaired by enabling this option.

Exact allowance catalogs
------------------------
The catalog subcommand explicitly snapshots regular files under the chosen root
(or a single file), including symlinked files. --root never authorizes directory
discovery. Each repeated --directory separately snapshots ONE exact directory:
  "directories": [
    {"path": "/exact/directory", "canonicalPath": "/exact/directory",
     "entries": ["one-immediate-entry", "another"]}
  ]
The entry list contains all immediate names, including hidden names but excluding
"." and "..". It is not a glob or recursive inventory, and grants NO child file
content reads. Use directory rules only for the two named external runtime
selection directories and the reviewed sysfs NUMA directory in this profile.
Do not use one to exempt app/toolset discovery.

Directory identity and membership must match at analysis time AND each traced
enumeration must expose the same complete entry set and reach EOF. -v is needed:
old traces containing only "/* N entries */" cannot validate directory rules.
Missing/extra entries, missing EOF or abbreviated trace entries fail closed.
Directory-handle opens are separately reported; without getdents64 they are not
treated as directory-content discovery (strict-probes can still reject them).
This is not an atomic filesystem snapshot: changes between observations, entry
inode/type/content replacement or changes undone between observations are not
proved absent. It validates observed name sets, not child bytes or open-ended
future discovery. Review/snapshot these immutable runtime directories BEFORE
capture. A stale catalog must not be refreshed merely to bless unexpected reads.

Use it ONLY on the external runtime installation, not an entire SDK/workspace.
All runtime files remain individually listed and reported, not prefix exemptions.
New runtime files require a new catalog.

Author platform-files.json explicitly, for example:
  {
    "schemaVersion": 1,
    "files": [
      {"path": "/etc/ld.so.cache", "canonicalPath": "/etc/ld.so.cache"},
      {"path": "/lib64/ld-linux-x86-64.so.2",
       "canonicalPath": "/usr/lib64/ld-linux-x86-64.so.2"}
    ]
  }
Replace these examples with exact paths on YOUR machine. Repeat --runtime-catalog
or --platform-catalog to combine catalogs. A file entry can also be an absolute
string; its canonical path is then resolved at analysis time. Explicit
path/canonicalPath pairs are preferred to detect changed symlink targets.
Missing exact file paths can admit corresponding negative probes. Directories
in the files array are rejected, not expanded into subtree permissions. Catalog contents are
trusted policy inputs; review them. No source, workspace, home, /proc, /sys,
/dev, locale, or loader prefix exemptions are built in.
Unexpected runtime probes must be explicitly cataloged or remain undeclared.
Reviewed OS/runtime files (for example exact OpenSSL DSOs/config, localtime or
NSS/account lookup files) remain machine-specific execution-image assumptions,
separate from product input completeness. They do NOT establish portable
hermeticity or safe content caching. Document per-file reasons and canonical
identities in a separate catalog; do not admit config includes, modules, home
files or directories merely because a reviewed runtime resource references them.

Process-local and self-created runtime observations (explicit opt-in)
--------------------------------------------------------------------
/proc/self is resolved with the traced process identity (CLONE_THREAD uses the
tracked thread-group PID), never the analyzer's PID. This correction is applied
even WITHOUT allowances. Proc magic aliases are rejected in exact file catalogs.
--allow-runtime-proc authorizes only maps, mountinfo, cgroup, readlink of exe,
readlink of self, and task/OWN-TID/comm. The target process must be traced in the
same action execution family; the thread must belong to that tracked process.
Unrelated processes, unknown TIDs, environ, fd directories, directory enumeration
and other /proc leaves remain denied. Every use records its leaf rule, processId
and actionFamily; no /proc tree exemption exists.

--allow-case-sensitivity-probe applies ONLY to the initial successful
O_CREAT|O_EXCL open of CASESENSITIVETEST[0-9a-f]{32}, followed by same-family
successful unlink of that exact path. It observes a newly created object, not
pre-existing input bytes. Later opens, arbitrary scratch names, missing exclusive
creation or missing unlink receive NO allowance. Every candidate and applied
rule is reported, without a /tmp prefix exemption.

MSBuild Framework/FileUtilities.cs computes this private case fact with a
DeleteOnClose scratch file; the action invocation has no explicit filesystem
case-sensitivity fact/setter. Linux OS identity does not prove a mount's casing.
Do not silently replace this probe with an OS assumption. To keep the probe in
an isolated working area, set TMPDIR and select it while constructing the graph:
  TMPDIR=/absolute/isolated/work ... build ... -p:MSBuildActionEnvironment=TMPDIR
The action host otherwise clears unselected environment, including TMPDIR.

Private response-file provenance (separate opt-in)
-------------------------------------------------
ToolTask can open a response file with O_WRONLY|O_CREAT and then reset it with
ftruncate(fd,0), rather than using O_TRUNC. The default %file trace DOES NOT
observe ftruncate. Do not infer initialization from O_CREAT or managed API intent.
For NEW captures add --response-file-provenance to the trace command. It adds:
  ftruncate,ftruncate64,close,close_range,dup,dup2,dup3,fcntl,fchmod,fchown
The current version also captures pipe/pipe2, socket/socketpair/accept,
eventfd/epoll/inotify/signalfd/timerfd, pidfd_open and memfd allocations, plus
potential descriptor import/opaque transitions that are rejected on successful
use unless explicitly supported (see FD_TRACE in audit.py). It does not capture
read/write payload bytes or add any content/resource allowance.

Version 2 replaces -ttt with --absolute-timestamps=unix,ns and adds
--syscall-times=ns (-T with nanosecond precision). Capture records
responseFileTraceProfile=2, fdLifetimeTraceProfile=2 and the exact syscall
selection. Both seccomp startup and workload use those same timing/filter flags.
Missing durations, inadequate timestamp precision and changed selections fail.
Version-1 captures retain their old conservative behavior; missing timing or
allocation evidence is never synthesized to make an earlier failed run pass.
Then explicitly add --allow-response-file-scratch to analyze.

This rule grants only successful child O_RDONLY opens of the exact .rsp object
with ALL these observed conditions:
  * Its immediate directory was newly mkdir'ed with requested mode exactly 0700,
    by the action-host process, directly inside an absolute TMPDIR/TMP/TEMP
    explicitly captured in THAT action descriptor. Existing directories and
    broad temp-root permissions never qualify.
  * Exactly one same-host O_WRONLY|O_CREAT open, with returned -yy canonical path
    equal to its logical spelling (no symlink aliases), is initialized by
    O_EXCL, O_TRUNC, or one successful same-fd ftruncate/ftruncate64(fd,0).
    Open-or-create alone, nonzero/failed resets and read-write creators fail.
  * Initialization and writer close finish before a successful declared-content
    executable child exec whose argv names @EXACT_RESPONSE_PATH. Only that child
    process/thread group may read it; each read fd closes before host unlink.
  * The same action-host process successfully unlinks the exact file; its entire
    traced family exits successfully. No cross-family accesses, extra writers,
    fd duplication/range ambiguity, path/ancestor permission/ownership changes,
    links/renames, unresolved calls or incomplete captures may conflict.
  * The file is not a declared/content input, measured output or generated tree.
    Such paths retain ordinary input/self-output semantics, never scratch status.

The rule uses syscall completion timestamps as well as entry ordering. Sequential
child reopens are supported; arbitrary fd transfers/aliases are not. It does NOT
admit sibling files, directory enumeration, metadata/negative probes, arbitrary
.rsp files, all files under TMPDIR, or TranslateSource/product scratch. A rejected
candidate stays undeclared and includes explicit rejection reasons.
responseFileScratchCandidates records provenance, initialization, lifecycle and
rejections. responseFileScratchAllowanceUsage records each actually admitted read,
separate from measured self-output and runtime/case-probe allowances.

This is observational provenance, not a protected scratch sandbox. Untraced
same-user processes, filesystem/mount races, pre-existing inherited fds and
unobserved fd transfers/writes remain limitations; no payload content is verified.
For simplicity any unresolved/incomplete event anywhere in the capture disables
these admissions. Failed commands or changed captured graph/sidecars do too.
Use a private working root and a minimal non-secret outer environment: strace -v
expands exec environments into raw logs. Preserve all raw captures and use a
restrictive caller umask (for example 077); no trace sampling/truncation is safe.

Common action-host file staging (opt-in)
---------------------------------------
Capture with --response-file-provenance (the unchanged full fd-lifecycle
selection), then add --allow-host-staging when analyzing. If compiler response
files are present, also retain --allow-response-file-scratch. --seccomp-bpf
remains an independent capture opt-in; its verification requirements are unchanged.
No graph rewrite, staging-root catalog, or source-directory snapshot is needed.

The supported common FileStagingContext contract requires exactly one successful
same-host mkdir(...,0700) of msbuild-stage-<32 lowercase hexadecimal digits>,
directly under the effective captured absolute TMPDIR, TMP, or TEMP (in that
priority order). Ambient/default, relative, symlinked-parent and shared/preexisting
roots are not supported. Materializer actions do not require a staging root.
Every declared input must have one host-created absolute file symlink at
ROOT/execroot/root/ABSOLUTE_LOGICAL_PATH, pointing to that exact DeclaredInputs
spelling AND admitted by the original Ninja content edge/generated-tree contract.
Canonical identity alone, an order-only edge, an implicit tool file not declared
as an input alias, or a filename resembling a staging path is insufficient.

The auditor reconstructs mkdir, exact aliases, file creation, fd identity,
supported fd controls, internal regular-file renames and deletion in trace time.
Staging may already have been removed when analysis runs. Input alias recreation,
write-capable alias opens, hardlinks, imports/exports, directory/alias renames,
ancestor replacement, dot-dot staging paths, ownership/root-permission changes,
unproven deleted fds and unsupported mutations reject the proof. Original input
symlinks/targets must still be stable; untraced actors/mount races are not modeled.

A scratch/output read needs an individually recorded new regular-file object in
this proven initially empty namespace, with completed parent creation and matching
-yy fd identity. A first writable O_CREAT open can establish a NEW object only
when the complete namespace ledger proves that name absent; this is NOT a generic
O_CREAT allowance. Existing/unobserved objects remain rejected even with O_TRUNC.
Internal file renames preserve object generations. Zero/nonnegative fd truncation
of these new files and ordinary file permission modes are supported, not new
external data sources. Deleted fd annotations are accepted only for an already
bound object with observed unlink/replacement history, not by stripping suffixes.
Write-only publication siblings outside staging receive no new read permission.

Each directory enumeration must have its own captured directory fd, exact
trace-born membership and EOF. Cleanup may remove already enumerated entries;
unseen removals, additions during enumeration, extra/missing names and partial
enumerations reject the proof. This inventory comes from explicit aliases and
observed new objects, NEVER discovery of a source/task directory. Existing
runtime/platform directory catalogs are unchanged.

Response files remain under the stricter separate writer-close -> declared child
exec @file -> child read/close -> host unlink rule. Only a successfully proven
ROOT/scratch may additionally serve as that family's effective temporary parent;
an RSP may also be created directly in an individually proven fresh directory,
including ROOT/scratch or a mapped task working directory such as illink-work.
Its 0777 mkdir request is accepted ONLY beneath the verified immutable exclusive
0700 staging root, with the exact captured directory birth/object matched to the
complete namespace proof. Shared/preexisting or symlinked directories and imported
files cannot qualify; this is not a generated execroot-file prefix allowance.
No arbitrary 0777 temporary directory is admitted. An executable staging
alias counts as declared only after its complete host-staging input-alias proof
passes (exact DeclaredInputs AND Ninja content edge), with that proof recorded
on the child execution. Exclusive/truncating initialization, writer/reader close,
@argument, same-family ownership, unlink and capture-completeness requirements
remain unchanged. General staging scratch cannot override a rejected RSP read.

Concurrent descriptor reuse (version-2 captures)
-----------------------------------------------
Shared CLONE_FILES tables use individually versioned descriptor generations,
not the last object printed for an fd number in syscall-entry order. Successful
allocations become usable only after their observed completion. A close consumes
the already completed live generation at entry; an overlapping ordinary
allocation cannot replace that live fd and may complete after that close frees
the number. This inference uses observed allocation/close transitions and kernel
fd-table constraints, NOT a path annotation alone. Exact -yy object identity,
input-alias declarations/content edges, directory inventories and cleanup
requirements are still separately checked.

Use before allocation completion, close/use overlap, competing atomic target
replacement, overlapping same-thread intervals/timing discontinuities, ambiguous
fd-table copies/exec, imports, unsupported successful
fcntl/ioctl transitions and close_range fail closed. Conservative supported
ioctl queries are TCGETS, TCGETS2, TIOCGWINSZ, FIONREAD and FIONBIO; they grant no
file access. Atomic replacement of a private fd is currently unsupported.
Ordinary dup/fcntl duplication propagates only a proven source generation.
Relative private dirfd accesses additionally require that exact directory's
captured generation. fdLifetimeProof reports verification/allocation/reuse
counts; version-2 content-open/directory observations record generation IDs
and completion timestamps. Any lifetime ambiguity disables staging/RSP proofs.

This is a supported observational Linux syscall subset, not a general kernel
execution-order oracle. Inherited descriptors, untraced actors, transfers through
unsupported mechanisms and new kernel APIs are not made trustworthy by -T.
No arbitrary ordering is invented for genuinely ambiguous generations. Earlier
captures without these timing/allocation transitions must remain rejected when
their lifecycle cannot be established.

Admission categories are hostStagingInputAlias, hostStagingOutput,
hostStagingScratch, hostStagingDirectory and hostStagingProbe. Each admitted use
records stagingRoot/objectId. hostStagingCandidates records roots, object
generations/history, exact enumeration evidence, cleanup and rejection reasons;
hostStagingAllowanceUsage records actual admissions; hostStagingViolations records
missing/multiple roots. Root rejection makes analysis fail, including when no
otherwise-undeclared content read remains. Any incomplete/unresolved capture,
changed captured inputs, missing lifecycle profile or failed family prevents
staging admissions. These are observational proofs, NOT OS confinement, payload
validation or a general write-footprint audit; inherited/unobserved fd transfers
and higher-priority competing seccomp filters remain limitations.

Admissions and attribution
--------------------------
Action identity is --invocation DESCRIPTOR or --materialize-tree DESCRIPTOR ROOT
in a successful execve/execveat argv, matched against the Ninja rule command.
Children and compiler processes inherit their parent's action; later matching
action execs acquire their own identity. Controller/Ninja/shell-before-action
events are counted separately, not silently assigned to an action. Fork, vfork,
clone, clone3, chdir, fchdir and CLONE_FS cwd sharing are tracked. -yy fd path
annotations resolve dirfd-relative operations and directory enumerations; a
missing/ambiguous annotation is unresolved, never an implicit allowance.

Content admissions:
  contentInput: exact explicit + implicit Ninja content paths and the descriptor.
  selfOutput: exact Ninja/DeclaredOutputs paths, separately counted.
  selfOutputTree: dynamically named descendants of DeclaredOutputTrees roots.
  generatedTreeInput: dynamically named descendants only when a Ninja CONTENT
    input names a root registered in a producer's DeclaredOutputTrees.
  runtime/platform: exact catalog path + canonical target pairs, with catalog
    provenance and each use included in the report.
  runtimeDirectory/platformDirectory: separate fixed-name directory rules.
  runtimeProc: one explicitly enabled, validated action-local proc leaf.
  caseSensitivityProbe: initial exclusive-created/unlinked named scratch open.
  responseFileScratch: separately proven private host-to-child transient .rsp.

DeclaredInputs are reported but do not grant permission missing from the Ninja
content edge. Order-only (||) prerequisites NEVER grant content admission.
Directories do not implicitly admit child file opens. Dynamic generated trees
are the explicit exception: their membership is execution-defined, not checked
against an archive/receipt member inventory. A materializer's receipt and tree
are self-outputs. Dyndep files and archives must appear on the content edge to
be content inputs. This auditor does not modify/load Ninja dyndeps into the graph.
Both logical and canonical paths must match policy; canonical aliases of exact
declared files are allowed, never arbitrary siblings. Tree accesses must remain
inside the canonical tree, including when a member is a symlink.

Supported observation profile and limitations
--------------------------------------------
Successful open/openat/openat2 reads (including O_RDWR), execve/execveat, readlink/
readlinkat and getdents64 enumeration are content observations. Even an empty
directory enumeration counts. O_WRONLY opens are writes, not reads; O_CREAT alone
does NOT make an open write-only. O_PATH opens are metadata probes.
O_DIRECTORY opens are directoryHandle observations, separate from getdents64.
stat/lstat/access/statfs/xattr queries and their supported *at variants are
metadata probes; unsuccessful opens/queries are negative probes. --strict-probes
makes undeclared metadata/negative probes fail as well. Without it these remain
fully reported. Directory metadata is admitted only by a matching valid exact
directory rule, never by file membership. Write syscalls normally do not grant
read admission; the optional response-file profile uses a narrowly proved
initialization/deletion lifecycle. This is NOT a write-footprint auditor.

Per-PID unfinished/resumed pairs are reconstructed at entry timestamps. Missing
pairs, process exit markers, child logs, unknown traced syscalls, truncated C
strings/argv and unresolved paths make analysis fail. Unsupported Ninja includes,
variables, arbitrary command forms and non-action rules (except emitted cleanup/
phony rules) are rejected. Cleanup execution is not an audited action profile.
The parser targets genbuild's emitted Ninja subset, not arbitrary Ninja projects.

NOT covered: inherited/pre-opened descriptors, reads/mmap without a traced path
open, kernel-internal interpreter/loader reads, directory data exposed by other
syscalls, io_uring, network, environment inputs, write correctness or unexecuted
actions. The trace expression intentionally does not capture read/mmap bytes.
An executable script's implicit shebang interpreter is not independently observed.
Successful open is a conservative content-read candidate, not proof bytes were
consumed. Canonical fallback for operations without returned fd annotations uses
the analysis-time filesystem EXCEPT known /proc process aliases, which use trace
identity, and the explicitly proven common-host staging namespace above. Other
path replacement, symlink races or mount namespace changes are not reconstructed.
Unknown namespace-related traced calls fail, but
the trace profile cannot detect every namespace mutation. All events are loaded/
sorted in memory; budget memory/storage for large runtime traces. Prefer an
isolated product smoke first, then a fresh full action execution.

JSON report, schemaVersion 1
----------------------------
Top-level keys:
  graph, graphSha256, strictProbes, ok, commandExitCode (capture analysis only);
  actions: observed action objects with id/mode/invocation/taskType/taskAssembly,
    workingDirectory, contentInputs, declaredInputs, declaredOutputs, outputs, trees, orderOnly,
    stagingTempParent (first captured TMPDIR/TMP/TEMP, not an allowance),
    pids, counts by admission, scratchRoots (selected absolute temp variables),
    dynamicTrees [logicalRoot, canonicalRoot, kind];
  undeclaredReads: unadmitted successful content-open/exec/readlink/enumeration;
  metadataProbes, negativeProbes: all such observations, admitted or not;
  runtimeAllowanceUsage, platformAllowanceUsage: each used allowance;
  directoryHandleOpens: handle opens, even when no directory data was read;
  directoryAllowanceUsage, directoryCatalogMismatches: fixed-membership evidence;
  runtimeProcAllowanceUsage, runtimeScratchAllowanceUsage: opt-in rule uses;
  selfCreatedProbes: exclusive-created case-probe candidates and unlink evidence;
  responseFileScratchCandidates, responseFileScratchAllowanceUsage:
    optional response-file lifecycle proofs/rejections and admitted child reads;
  hostStagingCandidates, hostStagingAllowanceUsage, hostStagingViolations:
    present with --allow-host-staging; private namespace proofs/uses/rejections;
  allowanceRules: complete runtime/platform exact catalog rules, even if unused;
  unresolved, incompleteness: raw event/error context where available;
  controller: {events: count, pids: [...]};
  limitations: explicit analysis qualifications.

Observation keys: action, pid, timestamp, syscall, path, canonicalPath, kind,
admission (null if undeclared), result, processId, actionFamily. File/directory
uses have catalog; process/scratch uses name their explicit rule.
Admission counts include probes; self-output reads remain separately categorized.
Action counts avoid retaining all successfully declared content observations.

Exit codes: analyze 0 = no observed violations/incompleteness in this profile;
1 = violations, strict undeclared probes or incomplete/failed capture;
2 = CLI, filesystem, catalog, graph or trace-loading error. Input errors print to
stderr; those fatal setup errors do not promise a JSON report. Neither 0 nor a
complete report is a sandbox/strict hermeticity guarantee.

Task-host resolver seam
-----------------------
TaskAssemblyLoadContext constructs AssemblyDependencyResolver only when the
component-adjacent .deps.json exists. An existing manifest retains normal runtime
dependency precedence/errors. Without one, exact adjacent AssemblyName.dll then
AssemblyName.exe are probed, followed by normal host fallback. Shared ITask and
TaskItem assembly identities and the Microsoft.Build engine rejection remain.
This avoids hostpolicy's missing-deps ambient directory enumeration. Manifestless
dependencies must use their exact assembly-name filename casing; arbitrary
filename aliases/mis-cased neighbors require an explicit deps manifest rather
than discovery. This is a deliberate restricted-host contract, not a general
replacement for runtime assembly discovery.
